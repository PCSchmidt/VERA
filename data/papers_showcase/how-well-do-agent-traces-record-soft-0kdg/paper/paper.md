# Trace Representation and Storage in Coding-Agent Harnesses: Evidence on Progress Signals, Log Formats, and Retrieval Backends

## Abstract

This review asks how coding-agent harness traces represent development progress, how formats and logging granularity differ, and how far traces are reported to be stored and mined with vector databases. The evidence shows that agent work has moved toward agentic, terminal-based settings in which agents act directly on repositories and build systems, and that trajectory analysis is an emerging way to understand them. Trace representations vary by purpose. Logs have been normalized into thought-action-result triples over 120 trajectories, SWE-agent releases trajectories and execution traces, and an observability taxonomy defines explicit task status fields. Persistence is framed as a choice among append-only logs, structured databases, checkpoint snapshots, and stateless designs. The one harness analyzed in detail, Claude Code, is reported to use append-only durable state. Vector storage evidence is mixed: Claude Code's memory retrieval uses no embeddings and relies on an LLM scan of file headers, while a survey reports that DroidAgent keeps embedded history in an external embedding database. Other approaches include a signed event log inside git and event sourcing with negligible reported overhead. The claims give no evidence that vector databases dominate, and observability standards are described as incomplete for agents. Open questions remain: native schemas for edits, test results, and commits; relative storage prevalence; the inspectability trade-off in trace mining; and whether git-kept logs reveal failures that pull-request history hides.

## Introduction

AI-assisted software development has moved from autocomplete-style tools toward agentic systems [R12]. Many software engineering tasks are performed in terminal-based environments, where agents interact directly with repositories, dependencies, and build systems through the command line [R15]. The reliability stakes are described in terms of silent error propagation [R15]. Because agents act through terminal commands on repositories and trajectory analysis is described as an emerging paradigm for understanding and improving them, the records of what an agent did become a natural object of study alongside its final result.

Trajectory analysis has been described as an emerging paradigm for understanding and improving agents [R15]. One early study normalized agent logs into thought-action-result triples over 120 trajectories [R15]. A study of failure trajectories collected runs from OpenHands, MiniSWE, and Terminus2 on Terminal-Bench [R15].

SWE-agent introduced a custom agent-computer interface (ACI) that, according to its authors, significantly enhances an agent's ability to create and edit code files, navigate entire repositories, and execute tests and other programs [R5]. The SWE-agent authors also released trajectories and evaluation execution traces as open artifacts [R5]. OpenHands is presented as a platform for agents that write code, use a command line, and browse the web [R27]. Claude Code's architecture has been described by analyzing its publicly available source code and comparing it with two open-source agent systems, OpenClaw and Hermes Agent [R12].

Storage choices are framed as design trade-offs. Session persistence in coding agents involves a choice among append-only logs, structured databases, checkpoint snapshots, and stateless architectures [R12]. For memory, one analysis notes that embedding-based retrieval gains flexibility at the cost of inspectability [R12]. From an observability angle, a taxonomy of AgentOps tools identifies the artifacts and data that should be traced across an agent's lifecycle [R3]. The AgentOps taxonomy lists task status, such as pending, in progress, or completed, among the traced data [R3]. The sections that follow take up how these threads bear on trace content, format, granularity, and storage.

## Method

The question this paper answers was proposed by VERA from the user's topic and confirmed by the user: What does the published literature and public documentation of major coding-agent harnesses (e.g., SWE-agent, OpenHands, Claude Code, Aider, Codex CLI) show about how their traces represent software development progress (e.g., edits, test results, task state, commit history), how trace formats and logging granularity differ across harnesses, and to what extent traces are reported to be stored and mined using vector databases versus other approaches such as structured logs, relational stores, or observability platforms?

Search. 12 queries were sent to the paper-search services: “SWE-agent agent-computer interface language model software engineering”; “OpenHands open platform AI software developers generalist agents”; “Claude Code Aider Codex CLI coding agent comparison”; “agent trajectories dataset software engineering issue resolution”; “LLM agent trace logging observability tracing standard”; “mining agent execution traces process analysis software repair”; “vector database retrieval agent memory episodic experience”; “SWE-bench benchmark evaluation of language models on real GitHub issues”; “survey of LLM-based agents for software engineering”; “survey agent observability AgentOps monitoring LLM agents”; “failure modes of coding agents trajectory analysis why agents fail”; “commit history and test results as signals in agent-generated pull requests”. They retrieved 120 candidate papers. A relevance screen, judged on titles and abstracts, kept 20 and set aside 100.

Reading. Every kept paper was read at its abstract; 8 were also read in full text, and 12 at the abstract only. This gave 98 evidence passages, the only text the paper may quote.

Writing and checking. The evidence sections were drafted sentence by sentence; every sentence that attributes something to a source carries a quote copied from one of those passages. Each quote was checked to be verbatim in its source, and a judge other than the writer checked that the passage supports the sentence and that the quote alone states it; sentences that failed were repaired once or removed. 59 claims from 14 sources survived, resting on 43 distinct quotes (a quote used by more than one sentence is one piece of evidence). Sentences without a claim were checked too: a synthesis names the claims it rests on and was judged to follow from them; any other sentence was judged to state no fact. Interpretation sections, where present, rest only on those claims and are labelled as such.

Models. Written by anthropic/claude-sonnet-5.5; judged by anthropic/claude-sonnet-5.5, z-ai/glm-5.3-flash.

## How traces represent development progress: edits, tests, and task state

The passages below illustrate several ways in which traces encode what an agent did and how its task is progressing. A later study of CLI coding agent trajectories reports that Bouzenia et al. normalized agent logs into thought-action-result triples over 120 trajectories [R15]. In the SWE-bench construction pipeline, repository-specific parsers convert validation logs into mappings from each test to a fail or pass status [R68]. SWE-agent's failure analysis found that Failed Edit Recovery, where models fail to generate well-formed edits, made up 23.4% of unresolved instances [R5]. For explicit task state, the AgentOps taxonomy defines a Task Status field holding states such as pending, in progress or completed, together with the task's result [R3]. Trace representations in the passages include normalized thought-action-result triples over agent trajectories, per-test fail or pass mappings parsed from validation logs, and an explicit task-status field with states such as pending, in progress or completed.

## Trajectory and log formats across SWE-agent, OpenHands, and other harnesses

Bouzenia and colleagues unified the interaction logs of RepairAgent, AutoCodeRover, and OpenHands into a common format, capturing 120 trajectories and 2,822 LLM interactions [R114]. A later study describes that earlier work as normalizing agent logs into thought-action-result triples over 120 trajectories [R15]. The OpenHands Software Agent SDK paper reports that production deployment data show negligible event-sourcing overhead [R72]. The authors of Graphectory use it to automatically analyze 4000 trajectories from SWE-agent and OpenHands, run with a combination of four backbone LLMs on SWE-bench Verified issues [R28]. A survey of provenance states that logs give chronological observability but may not show which tool output changed the plan [R40]. A study of CLI agents collected 3,843 trajectories across OpenHands, MiniSWE, and Terminus2 on Terminal-Bench [R15]. Coordination records can also live in version control, as in grite, whose append-only signed event log is stored inside git [R84]. ## Claude Code session storage and memory retrieval without vector indexes

The Claude Code source analysis states that session persistence in coding agents involves a design choice between append-only logs, structured databases, checkpoint-based snapshots, and stateless architectures [R12]. The same analysis states that Claude Code's persistence design implements the append-only durable state principle [R12]. The abstract of that study lists append-oriented session storage among the systems surrounding the core loop [R12].

For memory retrieval, the Claude Code analysis reports that the system avoids embeddings and uses an LLM scan of file headers [R12]. The analysis states that CLAUDE.md files are plain-text Markdown rather than structured configuration or opaque database entries [R12]. The Claude Code analysis characterises retrieval-augmented approaches as gaining flexibility at the cost of inspectability [R12].

A broader software-engineering survey describes embedding-based memory as a storage format used by other agents [R41]. The survey describes a key-value pair memory format in which information received from agents is stored in an external memory, with a key extracted for the agents to query required history memories [R41]. Taken together, the sources place Claude Code's file-based, non-vector approach alongside vector-database memory that the survey documents in other agents.

The Claude Code analysis describes the experiential tier, meaning automatically curated playbooks of strategies learned from past sessions, as the natural next step [R12].

## Observability platforms and tracing standards for agents

The following paragraphs turn to how observability for agents is described across general frameworks and in coding-agent settings. The AgentOps study states that by adding traces, AgentOps captures the entire process from the moment a user sends a prompt to the final output [R3]. The same study reports that all tools listed in its Table 3 have implemented tracing functionality [R3]. The survey on evidence tracing says distributed observability frameworks such as OpenTelemetry model executions as traces and spans, which is useful for describing multi-step agent runs [R40].

AgentTelemetry reports that OpenTelemetry's GenAI semantic conventions leave five agent orchestration phases without span-level representation [R117]. The provenance survey likewise states that LLM agents add semantic and procedural objects that existing provenance and observability traditions do not fully capture [R40]. Two sources treat standard tracing as a base, with one reporting that AgentOps adds traces to capture the whole process from user prompt to final output, and the other noting that OpenTelemetry models executions as traces and spans that suit multi-step agent runs. Two further sources report that this base is incomplete, with one finding that OpenTelemetry's GenAI semantic conventions leave five agent orchestration phases without span-level representation, and the other stating that LLM agents add semantic and procedural objects that existing provenance and observability traditions do not fully capture.

For coding agents specifically, the AgentTelemetry case study on SWE-bench Lite reports that 84 of 112 runs exhausted the 8-iteration limit and were classified as reasoning loops [R117]. The grite study reports that its append-only, signed event log is stored inside git itself [R84]. The SWE-agent authors state that they open source inference and evaluation artifacts such as trajectories and evaluation execution traces [R5].

The Claude Code analysis says its cited sources do not settle whether evaluation scaffolding belongs inside the harness or outside it as a separate layer [R12].

## Git-native and structured-log approaches to history and coordination

The following discussion turns to how coordination and persistence designs are described across the available material. The grite study describes a coordination substrate that needs no central server and stores its records inside git itself [R84]. The grite authors report that the log is a mineable artefact from which failure modes such as conflicting edits and lock starvation are automatically recoverable with provenance, several invisible in pull-request history [R84]. The grite study also reports that every agent's copy of the log converges to the same state with no write silently dropped, where a file-based tracker loses concurrent writes [R84].

Claude Code's documentation-based analysis frames session persistence as a choice among several designs [R12]. The same analysis states that Claude Code's persistence design implements the append-only durable state principle [R12]. The analysis adds that Claude Code's project-level memory can be version-controlled alongside the codebase [R12]. The OpenHands SDK paper reports negligible event-sourcing overhead in production deployment data [R72].

## Gaps in the evidence: Aider, Codex CLI, and vector-database mining

The Codex CLI entry describes the tool as a command-line interface that acts like a coding assistant directly in the terminal [R107]. A study of CLI agent failures names Codex alongside Claude Code and Gemini CLI as examples of terminal-based products [R15].

The software-engineering agent survey reports that DroidAgent embeds textual history into vectors and stores them in an external embedding database [R41]. The Claude Code analysis states that the system does not use embeddings or a vector similarity index for memory retrieval [R12]. The Claude Code analysis also says that CLAUDE.md files are plain-text Markdown rather than structured configuration or opaque database entries [R12]. One survey reports that a research agent embeds textual history into vectors and keeps them in an external embedding database, while an analysis of a coding harness states that its memory retrieval uses no embeddings or vector similarity index and that its memory files are plain-text Markdown; the two differ on vector storage, and both address agent memory.

The provenance survey reports that it reviewed key provenance representations, including structured logs, execution graphs, evidence graphs, tool dependency graphs, memory provenance, and multi-agent communication traces [R40]. The grite work stores coordination records inside git as an append-only, signed event log [R84]. The SWE-agent paper releases trajectories and evaluation execution traces as open artifacts [R5].

## Discussion

*Interpretation: VERA's reading of the claims named after each statement, judged to follow from them; not checked against quotes.*

The claims agree that agent work has shifted toward agentic, terminal-based settings in which agents act directly on repositories and build systems, and that trajectory analysis is an emerging way to understand them (C1, C2, C4). Trace representations vary by purpose. One line normalizes logs into thought-action-result triples (120 trajectories), another releases trajectories and execution traces as open artifacts, and an observability taxonomy defines explicit task status fields (C5, C8, C18). Persistence is framed as a design choice among append-only logs, structured databases, checkpoint snapshots, and stateless designs, and the one harness analyzed in detail is reported to implement append-only durable state (C11, C28). On vector storage the claims pull apart. One harness analysis says memory retrieval uses no embeddings or vector index, and relies on an LLM scan of file headers. A software-engineering survey reports that DroidAgent stores embedded history in an external embedding database (C30, C55, C26). The Claude Code analysis characterises retrieval-augmented approaches as gaining flexibility at the cost of inspectability, and it notes that Claude Code avoids embeddings for memory retrieval and keeps CLAUDE.md as plain-text Markdown. Together these suggest that, in this analysis, the choice of storage affects how inspectable stored memory is. The claims do not directly show how this affects the minability of traces (C12, C32, C55, C56). Other approaches also appear: coordination records kept as a signed append-only event log inside git, and an event-sourcing design whose overhead is reported negligible in production data (C42, C51). Observability standards are described as incomplete for agents, since OpenTelemetry conventions leave some orchestration phases without span representation and provenance work says agents add objects existing traditions do not capture (C39, C40).

## Conclusions

*Interpretation: VERA's reading of the claims named after each statement, judged to follow from them; not checked against quotes.*

The claims show that traces are represented in several ways, including thought-action-result triples, released trajectories and execution traces, append-only logs, and event logs in git. Task state is explicit in at least one observability taxonomy (C5, C8, C18, C42). The claims give no evidence that vector databases are the dominant way to store or mine traces. The single vector-database example concerns a survey-reported agent's history, and one harness is reported to avoid embeddings (C26, C55). How edits, test results, and commit history are encoded in each harness's own trace remains unanswered, although one benchmark pipeline maps tests to fail or pass status (C16).

## A research agenda

*Interpretation: VERA's reading of the claims named after each statement, judged to follow from them; not checked against quotes.*

Compare the native trace schemas of the named harnesses field by field, covering edits, test outcomes, task status, and commits, since the claims describe only normalized or released forms (C5, C19, C43). Measure how often harness traces are stored in vector databases versus append-only logs, relational stores, or observability platforms. The claims offer only isolated examples of each (C11, C26, C28, C37). Test the claimed inspectability trade-off of embedding retrieval against plain-text or log-based memory on trace-mining tasks (C12, C31, C32). Evaluate whether standard observability conventions can represent coding-agent phases, building on the reported gaps and the SWE-bench Lite case study (C39, C41). Study whether mining logs kept in git recovers failure modes that pull-request history hides, beyond the grite setting (C46, C45).

## Threats to validity

Coverage. The paper rests on what 12 queries found; the search was not repeated for the paper. A finding reported as missing means these searches did not find it, not that it does not exist.

Depth of reading. 12 of 20 kept papers were read at the abstract only, so their methods and caveats are known only as their abstracts state them.

What the checks cover. Each claim was checked against the passage it quotes, not against the whole source or the wider literature. A claim can be supported by its quote and still leave out a qualification stated elsewhere in the paper it cites. Interpretation sections were judged to follow from the claims they name; they were not checked against the sources.

Same-family grading. The writer is a Claude model; the judges are a different model family, and any independent scoring of this paper by a Claude model shares the writer's family.
